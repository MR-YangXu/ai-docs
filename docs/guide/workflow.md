# 日常协作流程

## 核心理念 {#concepts}

AI 编程范式把一次改动组织为 **Plan（规划）→ Implement（执行）→ Review（复核）**。以当前仓库的事实约束生成，用检查与行为证据判断完成。

| 习惯 | 可执行的做法 |
| --- | --- |
| “帮我写一个页面” | 给出目标入口、交互和验收标准 |
| 一开始把整个仓库读一遍 | 从 profile 找一条相关调用链 |
| 看起来能运行就结束 | 报告实际检查与未验证事项 |
| 每次重新提示团队规范 | 长期约定写入 profile，当前需求写进任务 |

三个阶段可以连续完成。只有影响实现的关键事实不明确，或涉及不可逆操作时，才需要额外确认。

## 需求拆解 · Plan {#plan}

每次只选一个可以独立验收的增量：

```text
目标：根据附图，在当前项目实现订单管理页面。
入口：现有规则、已审查的 .ai-code/profile.md，以及其中推荐的参考页。
复用：已核实的搜索、表格、分页、字典、请求层与主题样式。
验收：布局对应图片；筛选与重置生效；统计、分页、详情与导出行为一致。
范围：订单页面及必要的现有路由接入，数据模式与待联调项明确。
```

先读 profile 相关条目、一份路由、参考页前 120 行。组件与 Hook 只定位所需契约和一处调用。没有档案时使用相邻实现并注明缺口，不为日常任务补建一套索引。

## 代码生成 · Implement {#implement}

按已安装的任务技能实现，每份技能在会话中读一次。普通后台页使用 `ai-code-admin`；修改接口、路由、共享能力时才读对应技能。简单局部修复只核对被改文件和直接契约。

```text
按上述验收实现。简述拟改文件与复用依据后继续执行。
保留现有工作区改动，只处理任务范围。
导入、字段、事件与码值以当前源码为准。
默认只对改动文件运行本地 lint，输出检查摘要和待验证项。
```

共享能力能满足时直接使用；有缺口时说明参数、事件或布局差异，再选择兼容扩展或就近实现。不要照抄其他仓库组件名，也不要为了组织形式强行拆文件。

## 代码审查 · Review {#review}

检查差异、需求边界和检查证据。只要求审查时不修改代码。

```text
只审查本轮增量。每个问题给出位置、触发条件和影响。
核对验收是否落到代码，区分新增问题与历史问题。
没有证据的问题不报告为确定缺陷；未跑的检查不写成通过。
```

交付保留四项：完成内容、复用来源、实际验证、未验证事项。普通页面任务不默认执行全仓类型检查、构建、全量测试或浏览器自动化。

## 前端场景 {#frontend}

- 查询由页面持有；正在编辑的输入与已提交条件分开，搜索回第一页。
- 常量和字典只有一个定义来源，正确保留数值 `0` 与空值的区别。
- 复用已有 loading、失败、空结果和过期响应处理；动态选项写入当前页实例。
- 目录、路由、组件和国际化能力以当前源码及已审查的 profile 为准。

从[六步动手教程](/getting-started)完成接入并按截图生成页面。接着在同一个页面上[练习复制订单号](/examples/query-first-step)、快捷筛选、修复问题和检查结果。

## 后端场景 {#backend}

AI Code 当前聚焦 Vue 项目，不提供后端专项技能。后端可以沿用三阶段流程：先核实路由、鉴权、请求和响应契约，再实现服务逻辑，以现有测试验证输入边界、权限和事务。涉及写操作时核对重复提交、幂等与失败处理，接口契约变化同步检查调用方。

## 测试场景 {#testing}

按风险选择验证。行为回归、业务规则和复杂异步变更值得补测试；文案和布局调整不强制测试驱动开发。

已有测试设施时先写能复现问题的行为测试，确认失败原因，再做最小修复并运行相关测试。测试应验证用户结果和边界，避免只重复实现。缺少设施时如实记录，用代码路径或一次相关操作核对，不把“没有测试”算作通过。
