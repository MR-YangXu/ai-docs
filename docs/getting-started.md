# 快速上手

<p class="lead">把需求说清楚，让 AI 小步实现，再用证据完成交付。</p>

本页面向第一次接入 AI 编程工作流的开发者。你将获得一套可以直接使用的交互方式：**Plan（规划）→ Implement（执行）→ Review（复核）**。已有 Vue 3 项目可以沿用团队的 AI Code 规则，新项目也可以从一份 `AGENTS.md` 开始。

<ol class="workflow-steps" aria-label="AI 编程三阶段">
  <li><strong>Plan · 先规划</strong><span>理解需求，明确范围与验收条件。</span></li>
  <li><strong>Implement · 再执行</strong><span>复用已有能力，完成最小改动。</span></li>
  <li><strong>Review · 做复核</strong><span>检查差异，用验证结果交付。</span></li>
</ol>

::: tip 从一个小任务开始
先选一个能独立验收的改动，例如“为订单列表增加状态筛选”。**3 分钟是熟悉交互流程的阅读与练习目标**，不包含环境安装、模型等待或完整业务联调时间。
:::

## 什么是 AI 编程范式？ {#concepts}

AI 编程范式是一套人与 AI 协作交付软件的约定：开发者提供目标、约束和业务判断；AI 读取项目上下文，完成规划、实现与验证；团队依据真实代码和检查结果验收。

它将“描述一句需求，然后盲目接受生成结果”变成一个可以回溯的闭环。规则文件负责记录长期约定，当前任务负责说明具体需求，测试与审查负责给出反馈。

| 维度 | 盲目生成 | 按范式协作 |
| --- | --- | --- |
| 需求 | “帮我做一个订单系统” | “为已有列表增加状态筛选，提交后回到第一页” |
| 上下文 | 让模型猜目录与接口 | 提供实际页面、请求模块、参考实现和项目规则 |
| 过程 | 一次生成大量代码 | 拆小任务，逐步规划、实现和验证 |
| 正确性 | 页面看起来能用 | 核对契约、边界行为与实际检查结果 |
| 交付 | “代码写好了” | 说明改动、验证证据、未验证项和待联调项 |

**人负责明确“完成是什么”，AI 负责把实现与证据补齐。** 小改动可以在一次对话中完成三个阶段；涉及公开接口、数据迁移或需求分歧时，先解决关键决策，再进入依赖该决策的实现。

## 环境准备 {#environment}

### 步骤 1 · 打开正确的项目

使用 Cursor 打开业务项目根目录，确认 AI 可以读取源码、`package.json` 和相关文档。启用项目索引，并在编辑器的规则设置中核对生效的项目规则；界面入口以当前版本为准。

```bash
# 替换为你的业务项目目录
cd /path/to/your-project
node --version
```

运行时与包管理器以项目的版本声明、`packageManager` 和锁文件为准。已有 AI Code 接入要求见[项目操作手册](/handbook)；运行**这份 VitePress 文档站**建议使用 Node.js 22 或更高版本，两者不要混淆。

按现有锁文件选择一种安装命令：

::: code-group

```bash [npm]
npm install
```

```bash [pnpm]
pnpm install
```

```bash [yarn]
yarn install
```

:::

::: tip 编辑器准备完成的标志
AI 能指出目标文件、同类实现和实际可用的检查命令。先核对这些位置，再开始生成代码。模型选择、快捷键和插件数量不决定任务是否合格。
:::

### 步骤 2 · 引入项目规则

按项目现状选择一个入口：

| 你的项目 | 推荐方式 | 完成后核对 |
| --- | --- | --- |
| 现有 Vue 3 + Vite + TypeScript 项目 | 使用团队维护的 `@agent-xy/ai-code` | 场景、项目档案与质量命令状态 |
| 其他技术栈，或先试用通用流程 | 复制 [AGENTS.md 模板](/rules/agents-template#agents-md) | 路径和命令与仓库一致 |
| 需要 Cursor 按文件加载专项约定 | 在基础规则上补充 [MDC 规则](/rules/agents-template#mdc) | 匹配文件进入上下文时规则是否加载 |

首次接入 AI Code 的 Vue 项目，在业务项目根目录执行：

```bash
npx @agent-xy/ai-code init
```

根据提示选择通用、管理后台或移动端 H5 场景。然后核实 `.ai-code/profile.md` 中的项目约定，并执行：

```bash
# 仅适用于已经安装 @agent-xy/ai-code 的业务项目
npx ai-code status
npm run ai:check
```

最后一条按项目替换为 `pnpm run ai:check` 或 `yarn run ai:check`。已经存在 `.ai-code/config.json` 的项目安装依赖后直接检查状态；不要为每个开发任务重新初始化。

::: warning 区分用户约定与生成文件
AI Code 生成的 `.cursor/rules/ai-code.mdc` 等受控文件由包维护。长期业务约定写入 `.ai-code/profile.md`；新增通用规则前先核对是否重复或冲突。观察模式中，`ai:check` 正常退出可能仍包含缺失检查；`status` 中的 `available` 仅表示命令可用，不代表通过。
:::

### 步骤 3 · 按需连接 MCP 工具

MCP（Model Context Protocol，模型上下文协议）用于连接外部工具或资料，例如开发指南、接口文档和浏览器。**MCP 是可选能力，不是规则文件，也不会自动替你完成验证。** 只使用本地源码与规则即可完成下面的练习。

1. 在 Cursor 的 MCP 设置中添加所需服务，或合并项目的 `.cursor/mcp.json`。
2. 按[可复制的 MCP 配置](/rules/agents-template#mcp)接入开发指南服务。
3. 核对连接状态与工具列表，执行一次读取指南的操作，确认返回的是实际内容。
4. 把工具结果关联到当前需求，具体实现仍以本项目源码和已确认契约为依据。

准备完成后，发送一次上下文检查提示：

```text
请读取当前项目适用的规则和 package.json。
如果存在 .ai-code/profile.md，请核实其中与本任务有关的入口。
用简短列表说明：技术栈、推荐复用入口、实际存在的检查命令。
报告你已读取的文件；找不到的内容直接说明，不要猜测。
本轮只检查上下文，不修改业务代码。
```

## 3 分钟跑通一次工作流 {#workflow}

**练习需求：为现有订单列表增加状态筛选。** 以下路径是示例，发送提示前替换为仓库中真实存在的页面、请求模块和测试文件。状态值应从接口类型或已确认的文档读取，不能照抄示例猜测业务字段。

### 01 · 需求拆解 / Plan（规划） {#plan}

先给 AI 一个有边界的任务，让它查清复用来源并列出验收条件。

```text
请为现有订单列表增加状态筛选，本轮先规划。

页面：<实际订单列表路径>
接口依据：<实际请求模块或已确认接口文档>
参考实现：<已有筛选页面路径>

验收条件：
1. 选择状态并提交后，使用已确认的状态字段请求数据，页码回到 1。
2. 重置后恢复默认查询；“全部”按接口约定省略状态字段。
3. 快速连续查询时，较早的响应不能覆盖最新结果。
4. 请求失败时明确反馈，加载状态能够结束。

请先读取适用规则和相关源码，列出：
- 拟修改的文件、已有组件与请求能力的复用依据。
- 最小实现步骤，以及对应的测试或操作验证。
- 阻塞实现的契约缺口；没有缺口时明确说明。
本轮先不修改代码。
```

合格的规划应能回答“改哪里、复用什么、怎样证明完成”。例如：

| 子任务 | 实现范围 | 验收证据 |
| --- | --- | --- |
| 增加状态输入 | 复用现有筛选组件与状态常量 | 选项与接口状态一致，键盘可以操作 |
| 接入查询参数 | 沿用请求模块与分页逻辑 | 状态传参正确，提交与重置回到第一页 |
| 处理连续请求 | 检查已有取消或请求序号机制 | 人为让旧请求晚返回，结果仍对应最新条件 |
| 补充回归用例 | 沿用现有测试框架 | 新行为、失败路径与原有分页行为得到验证 |

::: tip 只暂停真正依赖决策的部分
如果接口没有状态字段，让 AI 明确缺口。你可以先授权完成界面和隔离的模拟数据，但这时交付范围是演示，真实接口联调需要单独验收。
:::

### 02 · 代码生成 / Implement（执行） {#implement}

确认方案后，明确授权实现。对于已授权且边界清楚的任务，AI 应连续完成实现、必要修复与验证，无需每改一行就询问。

```text
按上述方案实施，并完成本次范围内的验证。

先用项目已有测试框架为新增查询行为或已复现问题编写用例，
确认失败确实来自缺失的行为，再完成最小实现并重跑。
没有相关测试基础设施时先说明，并完成可执行的行为核对。

优先复用已核实的组件、常量和请求封装。
不要顺带迁移目录、替换依赖或重构无关模块。
沿用项目实际存在的检查命令，记录命令、范围和结果。
完成后给出变更摘要和验收证据；仅在必要业务决策缺失时询问。
```

下面以 TypeScript 查询参数为例说明“可验证的小增量”。**它是独立教学示例，不声明你的订单接口采用这些状态值**；业务实现应使用真实契约。测试示例要求项目已配置 Vitest。

::: code-group

```ts [先写测试 · order-query.test.ts]
import { describe, expect, it } from 'vitest'
import { createOrderQuery } from './order-query'

describe('提交订单筛选', () => {
  it('选择状态后带上状态，并回到第一页', () => {
    expect(createOrderQuery('pending')).toEqual({
      page: 1,
      status: 'pending',
    })
  })

  it('选择全部时不发送状态字段', () => {
    expect(createOrderQuery('all')).toEqual({ page: 1 })
    expect(createOrderQuery('all')).not.toHaveProperty('status')
  })
})
```

```ts [再做实现 · order-query.ts]
export type OrderStatus = 'pending' | 'completed'
export type StatusFilter = OrderStatus | 'all'

export interface OrderQuery {
  page: number
  status?: OrderStatus
}

// 用于提交筛选与重置；普通翻页应使用当前页码。
export function createOrderQuery(status: StatusFilter): OrderQuery {
  return status === 'all' ? { page: 1 } : { page: 1, status }
}
```

:::

采用 TDD（Test-Driven Development，测试驱动开发）时，可先建立可导入的函数骨架，让断言因行为尚未实现而失败。模块缺失、依赖未安装或测试配置报错，不算有效的“红灯”。完整规范见 [TDD 模板](/rules/agents-template#tdd)。

::: warning 一个通过的单元测试不等于功能完成
上面的测试只验证参数构造。页面事件是否正确接入、请求竞态、异常反馈和真实接口行为仍需组件测试、集成测试或实际操作验证。示例中的预期结果不是本项目已经执行过的业务测试结果。
:::

### 03 · 代码审查 / Review（复核） {#review}

实现结束后，先检查变更，再逐项核对验收条件。可以让同一个 AI 重新对照需求审查；条件允许时也可请另一位开发者复核关键行为。

```text
请对照原始验收条件审查本次差异，本轮只报告，不修改。

重点核对：
- 查询字段和状态值是否来自真实契约。
- 提交、重置和普通翻页是否各自保持正确行为。
- 旧响应、失败路径和加载结束是否处理完整。
- 新测试是否验证外部行为，是否遗漏原有功能回归。
- 是否引入重复组件、无关改动或未经验证的依赖。

只报告有证据的问题：给出文件位置、触发条件、影响和建议。
明确区分检查通过、执行失败、未执行以及待联调。
没有确认的问题时如实说明，不把推测写成缺陷。
```

对于已经接入 AI Code 的项目，在提交或合并前需要项目级检查时执行：

::: code-group

```bash [npm]
npm run ai:check
```

```bash [pnpm]
pnpm run ai:check
```

```bash [yarn]
yarn run ai:check
```

:::

其他项目运行规划阶段核实的命令。日常小改动先运行与影响范围相符的检查，项目级要求按团队约定执行。修复审查问题后重跑相关验证，再更新交付结论。

**一份可验收的交付说明：**

```text
已实现：<完成的行为及主要文件>
复用来源：<已有组件、请求模块、常量和参考页面>
检查结果：<实际执行的命令、范围、结果>
行为验证：<筛选、重置、竞态与失败路径的实际验证方式及结果>
未验证项：<尚未运行的检查和未覆盖的行为；没有则明确写无>
待联调项：<真实接口仍需确认的内容；没有则明确写无>
```

## 把流程用到真实项目 {#practices}

### 前端场景 {#frontend}

以 Vue 3 页面为例，先读相邻页面、组件源码和调用方，再选择复用方式。组件负责交互展示，Hook / Composable（组合式函数）负责可复用状态和生命周期，请求模块负责接口契约。

| 关注点 | 实施约定 | 验收方式 |
| --- | --- | --- |
| 状态与请求 | 区分输入条件、已提交条件与响应结果，处理取消或过期响应 | 快速切换筛选，检查最终结果与加载状态 |
| 组件复用 | 先检查属性、事件和插槽，必要时做兼容扩展 | 核对已有调用方，不复制整套组件 |
| 用户体验 | 覆盖加载、空态、异常和禁用状态，使用语义化表单控件 | 键盘操作、窄屏检查与失败路径验证 |
| 类型与契约 | 显式定义输入输出，沿用现有枚举和接口类型 | 类型检查加实际接口联调 |

**可直接复用的任务补充：**“同时验证加载、空态、失败与快速切换；列出复用组件的源码及一个已有调用方。”

### 后端场景 {#backend}

通用三阶段流程同样适用于后端。当前 AI Code 包针对 Vue 项目，**不要直接对后端仓库运行其初始化命令**；后端规则应根据实际框架、数据存储与测试方式填写。

| 关注点 | 实施约定 | 验收方式 |
| --- | --- | --- |
| 接口契约 | 先确定输入校验、响应结构、错误码与兼容策略 | 契约测试覆盖成功和非法输入 |
| 身份与权限 | 服务端校验访问范围，不能依赖前端隐藏按钮 | 未登录、无权限、跨用户访问用例 |
| 数据一致性 | 明确事务范围、幂等行为与重复请求处理 | 在测试环境验证失败回滚与重复提交 |
| 数据迁移 | 先说明影响范围、回滚方式和部署顺序 | 在隔离环境执行迁移并核对兼容性 |

**可直接复用的任务补充：**“先检查同类接口和数据库约束，列出失败路径；涉及持久化结构变化时先给出迁移与回滚方案。”

### 测试场景 {#testing}

对新业务逻辑和缺陷修复，优先采用 **Red（失败）→ Green（通过）→ Refactor（重构）**。对文案、排版等低风险修改，使用构建和实际页面检查；不要为实现细节编写没有业务价值的测试。

| 测试层次 | 最适合证明什么 | 订单筛选中的例子 |
| --- | --- | --- |
| 单元测试 | 确定性业务规则与边界值 | “全部”不携带状态字段，提交时页码为 1 |
| 组件 / 集成测试 | 事件、状态与依赖间协作 | 点击提交调用正确参数，旧响应不覆盖新响应 |
| E2E（端到端）测试 | 用户完整关键路径 | 从页面筛选到结果展示，再执行重置 |
| 人工验收 | 视觉、可访问性和真实环境行为 | 窄屏布局、键盘焦点、真实接口失败反馈 |

固定测试时钟和数据，使用可控制的响应模拟验证竞态，避免依赖任意等待时长。缺陷用例应能在修复前失败、修复后通过；模拟数据测试通过与真实系统联调通过应分别记录。

## 接下来做什么 {#next}

1. 复制并核实[团队规则模板](/rules/agents-template#agents-md)，让长期约定留在仓库。
2. Vue 项目按照[现有操作手册](/handbook)完成场景、档案和质量检查接入。
3. 选择一个小需求，按本页的三段提示走完一次闭环，把真实结果纳入团队审查。
